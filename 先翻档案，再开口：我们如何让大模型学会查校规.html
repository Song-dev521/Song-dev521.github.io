我们如何让大模型学会查校规

📅 2026年11月27日 📖 阅读约 12 分钟 # 项目 · RAG 实战复盘

写在前面：这是我这学期见习项目的完整复盘。我们组做了一个校园制度智能问答系统——58 份制度文档、7 个领域、867 个切片、9094 条条款入库，前端单页 6 个模式，后端 Flask + ChromaDB + GLM-4-Flash，最终部署上云，评委现场扫码就能访问。这篇不讲"我做了什么"的流水账，重点讲为什么这么设计，以及每个坑是怎么踩的、又是怎么爬出来的。项目已开源：gitee.com/Sstars-1/atlas-qa ↗

系统长什么样？

技术栈一句话：Python 3.11 · Flask · ChromaDB · Sentence-Transformers(bge) · 智谱 GLM-4-Flash · 原生 JS 单页前端 · 华为云 ECS 部署。

先回答一个问题：大模型为什么会"编校规"？

大模型有幻觉：会一本正经地编造一条不存在的校规。提示词里写"不要编造"只能约束行为，不能凭空增加知识——模型的参数里根本没有我们学校的宿舍管理条例。

RAG（检索增强生成）的思路是：把制度文档切片、向量化存进向量数据库；提问时先检索出最相关的几个片段，塞进提示词，让模型只依据材料作答。相当于把闭卷考试改成开卷考试——先帮它翻到那一页，它只要照着念就不会错。

我们做了个 A/B 对照实验验证这一点：

提示词版本提供材料？"宿舍几点断电"五次运行结果
只提问，无角色无约束❌基本每次都编出具体时间
加角色 + 强约束 + 兜底语句❌仍有若干次编造
在上一版基础上附真实片段✅五次全部准确

只加约束、不给材料，无法彻底阻止幻觉——这是整个项目里我最有底气的一条结论。

切片、向量、召回：三个决定成败的参数

为什么是 300 字重叠 50？

切片是 RAG 的地基。为什么必须切？一是 Embedding 模型有最大输入长度限制；二是一份文件常常一半讲宿舍、一半讲奖学金，整篇入库后向量语义混杂，检索时把不相关内容一起带进来。切开后每段只讲一件事，语义才"纯"。相邻切片保留 50 字重叠，是防止一句完整的话正好被切成两半、两边都检索不到完整语义。

切得太碎，片段脱离上下文，检索结果答非所问；切得太大，噪声多、提示词变长。我们前后试了好几组参数，300/50 是实测下来命中率和噪声的平衡点。这个参数没有万能答案，必须用自己的数据实测。

为什么召回固定 Top 3？

只取第一条容易漏掉正确条款；取五到十条噪声变多、提示词超长。还是平衡的艺术。

Embedding 凭什么比关键词检索强？

Embedding 把文本映射成高维向量，语义相近的文本距离近。用户问"宿舍几点熄灯"，制度原文写的是"学生公寓 23:30 断电"——关键词匹配不上"熄灯"，但向量空间里这两个句子距离很近，照样能召回。我们选了 bge-small-zh-v1.5，中文效果好、模型小，本地 CPU 就能跑编码，不花一分钱。

最惊艳的一幕：模型自己改写了追问

普通 RAG 是一条直线：检索 → 拼提示词 → 生成。智能体模式的区别是让模型自主决定调什么工具：我们给模型挂了 3 个工具（领域判定、条款检索、统计查询），模型拿到问题后自己决定先调哪个、拿到结果后再决定下一步，最多 3 轮。

答辩现场，主讲同学先问"宿舍几点断电"，再追问"那门禁呢"——"门禁"两个字在制度文档里根本检索不到任何东西，但工具轨迹里可以看到，模型把追问改写成了"宿舍门禁时间"再去检索，答案准确带出处。这个改写不是我们写代码做的，是模型在工具调用循环里自己完成的。现场有老师专门点了头。

防幻觉三道保险

  1. RAG 本身：只依据检索材料作答；
  2. 强约束提示词：写明"找不到信息就回复'暂无相关说明'"，而不是让它自由发挥；
  3. 展示出处：每条答案附文件名和条款位置，用户可核查，编没编一眼便知。

测试时故意问库外问题，系统稳定回复"暂无相关说明"。拒答能力比答得多更重要。

展开讲讲最痛的两个

坑一：明文密钥进了 Git 历史。开源清理仓库时发现，明文 API Key 被提交进了历史提交，而且不止一处（配置文档里一处、config.py 兜底配置里一处），users.json 里还有明文密码。删文件只是表面功夫——git 历史里旧提交照样能翻到。用 git-filter-repo 重写全部 59 个提交，把 Key 和敏感文件从历史中彻底抹除，再强制推送，最后三层验证（git log -S 搜关键词、逐提交逐文件 grep、核对本地与远端一致）。

我之前写过一篇《一次 GitHub 推送被拒的经历》，那次是 GitHub 的 Secret Scanning 帮我拦住了；这次是自己审出来的——两次经历合起来，三条教训刻进脑子里了：

  1. 密钥永远走环境变量，从第一个 config.py 开始就别写死；
  2. .gitignore 要在建仓当天配好，而不是泄露后补；
  3. 重写历史只管仓库本身——暴露过的密钥必须去平台作废重置，因为可能已经有人 clone 过。

坑二：强推挤掉了队友的提交。重写历史后强推，把队友刚推的提交从 master 上挤掉了——她的提交成了孤儿对象，Gitee 动态里显示"推送成功"，实际任何分支都不指向它。旧提交对象还在服务器上，但谁也 fetch 不到，最终只能靠拥有完整本地历史的她重新强推恢复。强推前必须确认所有协作者的本地状态——这不是一个人的仓库，核弹级操作动之前先在群里打个招呼，能省掉一场事故。

沉淀下来的工程习惯

  1. 配置集中管理：接口地址、密钥、模型名全在 config.py 一处，密钥只从环境变量读；
  2. 命令行先行：先写 CLI 验证检索和生成，跑通了再上 Flask 和前端——出问题时能立刻区分是 AI 链路的锅还是 Web 层的锅；
  3. 最小方式验证：能用 curl 测就不开网页，能把问题缩小到一行就不看整个系统；
  4. 排错四步法：先定层级（网络/网关/应用/AI）→ 最小验证 → 看日志 → 一次只改一处，改完立即复测；
  5. 把报错翻译成人话：401 查密钥、404 查地址、429 等等再试——把红色堆栈变成用户能懂的提示，是产品意识不只是技术细节；
  6. 接口契约先行：前后端先约定 JSON 字段再各干各的，联调几乎没有扯皮。

写在最后

做之前我以为核心难点是"怎么让模型更聪明"，做完发现核心难点是怎么让系统在真实环境里可靠地跑——离线加载、异常分级、拒答兜底、日志、快照、回滚，这些不起眼的环节才是工程的大头。检索质量决定回答质量：召回错了，后面生成得再漂亮也是错的。

下一步计划：把检索质量做成量化评测（构造标准问答对算命中率），补移动端适配，把"办事窗口状态"这类把制度数据变成实用工具的功能继续做深。
