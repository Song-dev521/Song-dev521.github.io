一次 GitHub 推送被拒的经历
我的阿里云密钥是如何暴露的

📅 2026年8月25日 📖 阅读约 5 分钟 # 安全 · 实战记录

写在前面：这是一次真实的踩坑记录。事情发生在今天，我花了一个下午才彻底解决。写下来，一是防止自己再犯，二是希望对正在经历同样问题的同学有所帮助。

事情是怎么发生的？

今天下午，我像往常一样执行 git push，准备把代码推送到 GitHub 仓库。结果，推送被拒绝了。GitHub 弹出了一段红色错误信息：

remote: error: GH013: Repository rule violations found for refs/heads/master.
remote: - Push cannot contain secrets
remote:
remote:       —— Alibaba Cloud AccessKey ID ————————————————————————
remote:        locations:
remote:          - commit: fdbacb84eab4001939c4829ce137ce450c5a17ac
remote:            path: sky-server/src/main/resources/application-dev.yml:14
remote:
remote:        (?) To push, remove secret from commit(s) or follow this URL to allow the secret.
remote:        https://github.com/.../security/secret-scanning/unblock-secret/...

那一刻我是懵的。 仔细一看，原来是我把阿里云的 AccessKey 硬编码在了配置文件里，而 GitHub 的 Secret Scanning 检测到了，直接拦住了我的推送。

为什么会出现这种情况？

回想起来，原因其实很简单：

  1. 图方便：开发的时候想着"反正先跑通再说"，直接把密钥写在了 application-dev.yml 里
  2. 提交了：git add . 的时候没多想，一起提交了
  3. 推了：git push 的时候 GitHub 检测到了

就这么三个步骤，密钥就这样暴露在了 Git 历史中。

我当时写的代码长这样：

# application-dev.yml
aliyun:
  oss:
    endpoint: oss-cn-chengdu.aliyuncs.com
    access-key-id: LTAI****************************        # ← 直接硬编码
    access-key-secret: ****************************************  # ← 直接硬编码
    bucket-name: stars-2026

现在回头看，这简直就是把家门钥匙挂在门口。🙃

GitHub 做了什么？

GitHub 有一个叫 Secret Scanning（密钥扫描） 的功能，它会自动扫描仓库中的代码，检测是否包含已知服务的密钥（阿里云、AWS、GitHub Token 等）。

一旦检测到，GitHub 会：

  • 阻止推送（如果开启了 Push Protection）
  • 发送安全警报给仓库管理员
  • 提供处理链接让你手动允许或修复

这次我被拦截了，说明 GitHub 的 Push Protection 确实在起作用。

我是怎么解决的？

方案一：允许密钥通过（临时方案）

GitHub 返回的错误信息里附带了两个链接，点进去后选择 "我待会儿会修好的"，然后点击 "请允许我揭露这个秘密"。

这样就能推送成功了。但 这个方案只是临时绕过去，密钥仍然在 Git 历史里，不安全。

方案二：彻底清理 Git 历史

既然密钥已经暴露在了历史里，那就需要把历史重写。

方式一：使用 git filter-repo

# 安装 git-filter-repo
pip install git-filter-repo

# 从历史中移除包含密钥的文件
git filter-repo --path sky-server/src/main/resources/application-dev.yml \
                --path sky-server/src/main/resources/application.yml \
                --invert-paths --force

# 重新添加远程仓库
git remote add origin https://github.com/Song-dev521/smart-order.git

# 强制推送
git push origin master --force

方式二：删除 .git 重新初始化

# 删除 .git 文件夹
rm -rf .git

# 重新初始化
git init

# 添加远程仓库
git remote add origin https://github.com/Song-dev521/smart-order.git

# 提交代码（只有一次提交，没有历史）
git add .
git commit -m "feat: 首次提交"

# 强制推送
git push origin master --force

我选了方式二，因为我的项目刚起步，历史不重要，干净最重要。

第三步：改用环境变量

清理完历史后，我把代码改成了这样：

# application.yml
aliyun:
  oss:
    endpoint: oss-cn-chengdu.aliyuncs.com
    access-key-id: ${ALIYUN_ACCESS_KEY_ID}
    access-key-secret: ${ALIYUN_ACCESS_KEY_SECRET}
    bucket-name: stars-2026

然后在 IDEA 的运行配置中设置环境变量：

ALIYUN_ACCESS_KEY_ID=你的AccessKeyID
ALIYUN_ACCESS_KEY_SECRET=你的AccessKeySecret

从此，密钥不再写在代码里。

密钥已经泄露了怎么办？

第一步：立即禁用泄露的密钥

  1. 登录阿里云控制台
  2. 进入 AccessKey 管理
  3. 找到泄露的 AccessKey
  4. 点击 禁用 → 确定

第二步：创建新的 AccessKey

  1. 点击 创建 AccessKey
  2. 复制并保存新的密钥
  3. 更新项目配置

我学到了什么？

做法安全性
硬编码在代码中❌ 极度危险
写在配置文件并提交❌ 危险
环境变量✅ 安全
配置中心✅ 安全

提交前检查敏感信息

grep -r "LTAI" . --exclude-dir=.git
grep -r "AKIA" . --exclude-dir=.git

写在最后

这次踩坑让我深刻记住了三个字：别硬编码。

如果你也在开发中遇到过类似的问题，别慌，这是很多开发者都会经历的。关键是：

  1. 立即禁用泄露的密钥
  2. 从 Git 历史中清理掉
  3. 改用环境变量
  4. 以后记住教训

你的代码值得被保护。从今天起，别再让密钥暴露在 Git 历史中了。 🔐
